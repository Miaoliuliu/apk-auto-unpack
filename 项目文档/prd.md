# 产品需求文档：APK 自动化脱壳与 URL 提取工具

**版本**：1.0  
**日期**：2026-08-21  
**作者**：Sarah（产品负责人）  
**质量评分**：93/100

---

## 1. 执行摘要

本项目要做的是一个本地化的 APK 分析工具：输入一个 APK 文件后，系统先识别是否加壳；如果无壳，直接遍历代码、资源和相关二进制内容提取 URL、域名和 IP；如果有壳，则识别壳类型，按壳类型调度对应脱壳插件，脱壳成功后再进入同样的 URL 提取流程。

前面的压测结论很明确：这个项目能做，但第一版不能承诺“支持所有壳”。最现实的做法是把它设计成插件化分析流水线，优先保证无壳分析稳定、壳识别可解释、失败原因可追踪，再逐步扩展壳支持范围。

---

## 2. 问题定义

### 2.1 当前情况

APK 分析通常要手工串联多个工具和步骤：壳识别、反编译、动态 dump、DEX 修复、字符串扫描、URL 去重和报告整理。遇到加固壳时，失败原因往往不透明，用户很难判断问题出在识别、脱壳、修复还是提取阶段。

### 2.2 目标方案

构建一个自动化工具，统一完成以下流程：

1. 输入 APK
2. 校验文件并提取基础元信息
3. 识别是否加壳及壳类型
4. 无壳则直接提取 URL
5. 有壳则调度对应脱壳插件
6. 脱壳成功后提取 URL
7. 输出结构化报告和清晰的错误状态

### 2.3 业务/工程价值

- 减少人工切换工具的时间
- 让 APK 分析流程可批量化、可复现
- 把失败状态显式化，便于排障和二次分析
- 为后续扩展更多壳支持、批处理和平台集成打基础

## 3. 成功指标

### 3.1 核心指标

- 无壳 APK URL 提取成功率：在测试集上达到 95%+
- 壳识别准确率：在已知样本上达到 90%+
- 首批支持壳的脱壳成功率：在指定样本集上达到 60%+
- 单 APK 分析耗时：无壳场景 60 秒内；有壳场景 5 分钟内给出结果或失败原因
- 报告可用性：100% 生成 JSON 报告，包含处理路径、结果、错误和版本信息

### 3.2 验证方式

使用 30-50 个 APK 样本构建回归集，覆盖：

- 无壳 APK
- 常见壳 APK
- 混淆但无壳 APK
- 识别失败样本
- 脱壳失败样本

每次迭代必须跑回归集，检查识别、脱壳、提取和报告是否回退。

## 5. 用户故事与验收标准

### 故事 1：识别 APK 是否加壳

**作为** Android 安全分析人员  
**我希望** 输入 APK 后自动识别是否加壳和壳类型  
**以便** 决定后续是否需要脱壳

**验收标准**
- [ ] 支持单文件 APK 输入
- [ ] 输出 APK 基础元信息：包名、版本、大小、hash、minSdk、targetSdk
- [ ] 无壳时输出 `packed=false`、`packer=none`
- [ ] 有壳时输出 `packed=true`、`packer`、`confidence`、命中特征
- [ ] 不确定时输出 `packed=unknown` 并列出候选壳

### 故事 2：无壳 APK 直接提取 URL

**作为** Android 安全分析人员  
**我希望** 无壳 APK 直接提取 URL、域名和 IP  
**以便** 快速得到网络行为线索

**验收标准**
- [ ] 不进入脱壳流程
- [ ] 遍历 `classes.dex`、资源、Manifest、assets 和 native 字符串
- [ ] 对 URL/domain/IP 去重并归一化
- [ ] 每条结果保留来源位置
- [ ] 空结果时输出 `url_count=0`，不视为失败

### 故事 3：有壳 APK 调度对应脱壳插件

**作为** Android 安全分析人员  
**我希望** 系统能按壳类型自动选择脱壳插件  
**以便** 少做手工切换

**验收标准**
- [ ] 壳类型能映射到插件
- [ ] 无插件时输出 `unpack_status=unsupported_packer`
- [ ] 插件执行成功后产出可分析代码文件
- [ ] 插件失败时输出阶段性错误：环境、启动、dump、修复、验证
- [ ] 脱壳产物进入统一 URL 提取流程

### 故事 4：生成结构化分析报告

**作为** 平台开发者  
**我希望** 每次分析都有稳定的机器可读报告  
**以便** 直接接入后续系统

**验收标准**
- [ ] 生成 JSON 报告
- [ ] 报告包含 `sample`、`packer_detection`、`unpack`、`extraction`、`urls`、`errors`
- [ ] 每条 URL 包含 `value`、`type`、`source_file`、`source_kind`、`business_likelihood`、`validation`
- [ ] CLI 退出码区分成功、无 URL、识别失败、脱壳失败、输入非法
- [ ] 支持指定输出目录

## 6. 功能需求

### 6.1 核心功能

**功能 1：APK 输入与校验**
- 说明：校验文件是否为有效 APK，提取基础元信息和 hash
- 流程：`analyze sample.apk -o out/`
- 边界：非 APK、损坏 APK、超大 APK、split APK、缺少 `classes.dex`
- 错误处理：明确错误码，不进入后续流程

**功能 2：壳识别**
- 说明：使用特征库识别常见壳/混淆/加固特征
- 流程：分析启动后自动执行，也可单独 `detect`
- 分流：无壳 → 直接提取 URL；dpt-shell → dpt 插件；常见厂商壳 → 该厂商插件；该厂商样本带 VMP 或自研保护（含原 JDog / 未知壳 / packhub）→ 标记转人工分析，不提取 URL。不按一代/二代分流（商业壳一二代混用）
- 边界：多壳特征、壳特征残留、未知壳
- 错误处理：低置信度进入 `unknown`，禁止强行脱壳

**功能 3：无壳 URL 提取**
- 说明：从 DEX、资源、Manifest、assets、native 字符串中提取 URL/domain/IP
- 流程：无壳分支自动反编译或解包后提取
- 边界：字符串拼接、base64、压缩资源、混淆变量名
- 错误处理：区分“无结果”和“提取失败”

**功能 4：脱壳插件框架**
- 说明：按壳类型调度插件，插件完成环境检查、执行、产物验证
- 流程：有壳分支自动匹配插件；无插件则返回不支持
- 边界：需要模拟器/设备、反调试、运行崩溃、多 dex
- 错误处理：插件必须返回标准状态码和阶段日志

**功能 5：结果归一化与报告**
- 说明：对 URL/domain/IP 去重、分类和输出
- 流程：所有分支进入统一报告层
- 边界：重复结果、协议缺失、内网地址、测试地址、广告/统计域名
- 错误处理：无法归类时保留 `unknown`

### 6.2 非目标

- 第一版不承诺支持所有 Android 壳
- 第一版不做云端 SaaS、账号系统、团队协作
- 第一版不做完整恶意行为判定
- 第一版不保证完整源码还原
- 第一版不做 GUI，除非 CLI MVP 已稳定

## 7. 技术约束

### 7.1 性能

- 无壳分析目标 < 60 秒
- 有壳分析默认超时 5 分钟，可配置
- 批量模式支持失败隔离和并发控制

### 7.2 安全

- 所有 APK 视为不可信输入，工作目录必须隔离
- 默认不执行 APK，动态脱壳必须显式启用
- 输出报告不得泄露本机敏感路径、环境变量或凭据

### 7.3 集成

- 壳识别：APKiD 或等价特征库
- 解包/反编译：jadx、apktool、androguard 至少选一条主路径
- 动态脱壳：Frida / objection / 自定义 dump 插件
- runtime：Android emulator 或测试设备

### 7.4 技术栈建议

- 第一版建议使用 Python 作为 CLI 主框架
- 插件接口建议采用 `plugins/unpackers/{packer_name}` 目录约定
- 输出格式优先支持 JSON、JSONL、CSV
- 平台优先兼容 Windows，同时保持 Linux/macOS 可迁移

## 8. MVP 范围与分期

### Phase 1：MVP

- APK 输入校验与基础元信息解析
- 壳识别：无壳 / 有壳 / unknown / packer type / confidence
- 无壳 APK URL 提取
- 结构化 JSON 报告
- 脱壳插件框架
- 只实现 1 个可验证插件或 mock 插件

**MVP 定义**：输入 APK 后，系统能稳定判断无壳/有壳，并对无壳 APK 输出可信 URL 报告；对有壳 APK 能识别壳类型，若支持则执行插件，若不支持则明确返回状态。

### Phase 2：增强

- 支持 1-2 类常见壳的真实脱壳流程
- 批量目录分析与 CSV/JSONL 汇总
- URL 分类：API、WebView、SDK、广告、统计、可疑 C2
- HTML 报告

### Phase 3：未来方向

- 动态流量抓取与静态结果合并
- URL 拼接还原、base64/加密字符串解码
- Web UI 或桌面端界面
- 样本库与任务队列调度

## 9. 风险评估

| 风险 | 概率 | 影响 | 缓解策略 |
|---|---|---|---|
| 自动脱壳成功率低 | 高 | 高 | 插件化设计；MVP 不承诺全壳支持；按壳分别维护测试集 |
| 壳识别误判 | 中 | 高 | 引入置信度和命中特征；低置信度进入 unknown |
| URL 误报/漏报 | 高 | 中 | 保留来源位置，分离业务相关性与语法/DNS/HTTP 验证状态；建立带标注的样本集 |
| 外部工具环境复杂 | 中 | 中 | 启动时做依赖检查；报告记录工具版本 |
| 动态脱壳不可信输入风险 | 中 | 高 | 默认关闭动态执行；要求隔离环境 |
| Windows 路径兼容性问题 | 中 | 中 | 统一使用 `pathlib`，覆盖空格/中文路径测试 |

- APK 样本测试集，至少 30 个
- 壳识别规则源
- 反编译工具链
- 动态脱壳环境

### 已知阻塞

- 首批支持壳类型未最终确定
- 样本集未建立前无法量化成功率
- URL 提取范围需在实现前明确：只提明文 URL，还是包含域名/IP/编码字符串

## 11. 验收标准

- 输入一个合法 APK，系统能完成解析并输出结果
- 无壳 APK 能稳定输出 URL/domain/IP
- 有壳 APK 能识别壳类型
- 不支持的壳能清晰提示 `unsupported_packer`
- 每次运行都生成结构化报告
- 失败时能明确指出失败阶段

## 12. 附录

### 术语

- APK：Android 应用安装包
- 壳/加固：对 APK 代码或 DEX 做保护、加密、动态加载或反分析处理
- 脱壳：恢复可分析的 DEX/代码产物
- URL 提取：从代码、资源、字符串、native 二进制中识别网络地址
