# 提交前代码审查与验证

用户准备提交代码（git commit、发起 Pull Request 或合并请求）时，**先完成本技能再提交**。未出【审查报告】不得 `git commit` / `gh pr create`。

## 核心原则

任何代码提交都必须经过实际测试与验证，不允许仅凭主观判断或口头承诺。审查结论必须基于可复现的证据（测试结果、日志、静态分析报告等）。

## 执行步骤（必须按序）

1. 取变更范围（并行）：
   - `git status`
   - `git diff` 与 `git diff --staged`
   - `git log`（最近若干条，对齐仓库风格）
2. 静态审查：读完全部新增/修改文件（含测试），对照下方「审查流程 · 静态审查」。
3. **动态验证（禁止跳过）**：在仓库内真实跑测试。按仓库现有方式选择命令，例如：
   - Python：`python -m pytest tests -q --tb=short`（本仓库优先用已装 pytest 的解释器）
   - 有 `package.json` 的脚本：`npm test` / 项目文档写明的命令
   - 只跑与变更相关的测试不够时，再跑对应套件或全量，避免漏回归
   - 覆盖率：仓库若已配置则带上并记录百分比；未配置则写「未配置，未测」并说明风险
   - 关键功能：用现有测试、CLI 或最小复现命令实际跑一遍，把命令与关键输出写入报告
4. 测试失败：**结论=不通过**，先修再重跑，不得带着失败提交。
5. 某项测试无法执行：在报告中写明原因和风险，**征得用户同意**后才可继续；不得假装已跑。
6. 输出【审查报告】。仅当结论为「通过」或用户接受「附条件通过」后，才执行用户要求的 commit / PR。

## 审查流程

### 1. 静态审查

代码规范：检查是否符合项目约定的编码风格（如 PEP 8、ESLint 规则等）。

逻辑正确性：逐模块审阅新增/修改的代码，确认逻辑无漏洞、边界条件处理完整。

安全风险：检查是否存在注入、越权、敏感信息泄露等安全问题。

依赖与兼容性：确认新增依赖合理、版本兼容，无破坏性变更。

### 2. 动态验证（必须执行）

单元测试：运行相关单元测试，确保全部通过。若测试覆盖不足，需补充测试用例。

集成测试：验证模块间交互正常，无回归问题。

实际运行验证：对于关键功能，需在本地或测试环境实际运行，并提供输出日志或截图作为证据。

性能与资源检查：若涉及性能敏感代码，需进行基准测试或内存分析。

### 3. 证据收集

记录所有测试命令及结果（通过/失败、覆盖率等）。

保存关键日志、截图或测试报告。

若某项测试无法执行，必须明确说明原因及风险，并征得用户同意后方可继续。

### 4. 审查结论

通过：所有测试通过，证据齐全，可提交。

附条件通过：存在轻微问题（如注释缺失、非关键警告），可先提交但需记录待办事项。

不通过：存在功能缺陷、测试失败或安全风险，必须修复后重新审查。

## 输出格式（每次审查后必须提供）

```text
【审查报告】
- 审查范围：列出变更文件或模块
- 静态审查发现：问题列表及严重程度
- 动态验证结果：
  - 测试命令：xxx
  - 测试结果：通过/失败（附关键输出）
  - 覆盖率：xx%
- 证据链接/截图：（如有）
- 结论：通过 / 附条件通过 / 不通过
- 遗留问题：（若有）
```

静态发现按严重程度标注：严重 / 中等 / 轻微。无问题写「无」。覆盖率未测写「未测」及原因，禁止填假数字。

## 禁止行为

仅凭“代码看起来没问题”等主观表述通过审查。

跳过动态验证直接给出结论。

伪造测试结果或证据。
